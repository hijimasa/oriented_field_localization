## 結論

秘密鍵、API token、password、開発機の絶対パス、第三者地図、rosbag、評価CSV、ログ、
ビルド生成物は追跡対象から検出されなかった。MITの`LICENSE`と`package.xml`の宣言も
一致しており、ROS非依存の単体テスト63項目、最小評価ハーネス、ROS 2 Humble上の
`colcon build`と3テストは成功した。

一方、既定のサービス起動では継続TRACKへ移れないことと、LiDARの取り付け変換を
適用しないことは、READMEが示す通常利用または実機利用に直接影響する。さらに、今回
削除対象になった未公開実装への言及は現行worktreeから除去できるものの、公開予定の
Git履歴には残る。少なくともHigh 3件の方針を決め、修正・テスト・再レビューが終わるまで
Public化を保留する。

## レビュー方法

主担当と独立レビュー担当の2系統で、source、header、launch、config、Docker、評価・
simulationスクリプト、日英README/docs、Git追跡対象と履歴を確認した。秘密情報のパターン

ROS 2 Humbleコンテナビルドを検査した。

## Critical

## High

### H1 — 既定のサービス起動では継続TRACKへ移行できない

READMEはサービスを呼んで推定を開始する手順と、収束後にTRACKで追従する動作を案内する。
しかし`auto_localize: false`では、`OflNode::workerLoop()`がサービス要求を1スキャン分で解除する。
TRACKへの遷移は`OflNode::onAccept()`で既定3回の連続採択を要求するため、サービスを1回
呼んだ通常手順ではGLOBALを1回実行して停止し、TRACKへ到達できない。

- 根拠: [`README.ja.md`](../../README.ja.md)、
  [`src/ofl_node.cpp`](../../src/ofl_node.cpp) の `workerLoop()` / `onAccept()`、
  [`config/params.yaml`](../../config/params.yaml) の `auto_localize` / `track_after_accepts`
- 推奨: サービス要求をTRACK遷移まで保持するか、サービス起動時の遷移規則を定義し直す。
  「サービス1回 → 継続TRACK」を確認するROS結合テストを追加する。

### H2 — LiDARと`base_frame`の外部パラメータを無視する

`OflNode::toBeams()`は`LaserScan.header.frame_id`を参照せず、スキャン原点基準のビームを
そのまま照合する。`publishPose()`は得られたスキャン原点の姿勢を`/initialpose`、
`map -> odom`または`map -> base_frame`へ使う。LiDARと`base_link`の並進・yawが一致しない
実機では、base姿勢に系統誤差が入る。simulation文書も現在の評価がxy一致を前提とすることを
明記している。

- 根拠: [`src/ofl_node.cpp`](../../src/ofl_node.cpp) の `toBeams()` / `publishPose()`、
  [`sim/README.md`](../../sim/README.md) の「LiDAR の取り付け位置」
- 推奨: スキャン時刻の`base_frame <- scan_frame`をTF2から取得して推定へ合成する。
  TF不在時の棄却・警告方針と、並進・回転オフセットを含む結合テストを追加する。

### H3 — 現行文書から削除しても、削除対象の旧記述はGit履歴に残る

現行worktreeでは削除対象語と未公開実装への参照は0件になったが、公開cloneから閲覧できる
過去commitには残る。最初の導入commitは`e298b1a`である。未公開実装の存在や名称自体を
Publicリポジトリから伏せる要件なら、現行ファイルの編集だけでは満たせない。

- 根拠: `git log --all -S<削除対象文字列>`、commit `e298b1a`
- 推奨: 現行版からの削除だけで十分かを公開責任者が判断する。履歴からも除去する場合は、
  公開前に`git filter-repo`等で履歴を書き換えるか、公開用orphan/squash履歴を作る。

## Medium

### M1 — 地図YAMLの対応範囲がmap_server互換より狭い

`OflNode::loadMapFromYaml()`は行単位の独自パーサで`image`、`resolution`、originのx/yだけを
読む。引用符付き・絶対image path、`negate`、`occupied_thresh`、`free_thresh`、`mode`、
origin yawを扱わず、不正な数値では`std::stod`例外で終了し得る。`OccupancyGrid`経路でも
originのquaternionを無視する。

- 推奨: YAMLライブラリまたはNav2 map I/Oを利用する。すぐに変更しない場合は対応範囲を
  明記し、絶対/相対path、引用、threshold、origin yaw、構文エラーをテストする。

### M2 — スキャン時刻とオドメトリ時刻が同期していない

最後に受信したodomを時刻情報なしで事前姿勢と`map -> odom`に使う一方、出力stampは
スキャン時刻である。通信遅延やpublish rate差があると、姿勢とstampが同じ時点を表さない。

- 推奨: TF2またはodom履歴からスキャン時刻の姿勢を補間し、取得不能時の方針を定める。

### M3 — パラメータ検証が不足している

`match_resolution <= 0`、負のsigma、極端なpool/level値などが除算ゼロ、OpenCV assertion、
過大確保につながり得る。未知の`tf_mode`は警告なしで`none`になる。

- 推奨: parameter descriptor/rangeと起動時の一括検証を追加し、不正値は具体的な理由で
  fail-fastする。

### M4 — 公開ライブラリとしてのinstall/exportが不完全

`oriented_field_matcher`をSTATIC libraryとして定義しpublic headerをinstallする一方、
library本体とCMake target/dependencyをinstall/exportしない。install後のdownstream packageは
headerを参照できてもリンクできない。

- 根拠: [`CMakeLists.txt`](../../CMakeLists.txt) の`add_library()`と`install()`
- 推奨: 外部APIならtarget、include、OpenCV/OpenMP依存をexportする。内部実装ならheaderを
  installせず、その契約を明記する。

### M5 — `localize()`の「スレッドセーフ」契約と実装が一致しない

headerは`localize()`をスレッドセーフと記すが、`localize()`と`track()`は同一instanceの
`impl_->stage`を更新する。同一instanceへの並行呼び出しはdata raceになる。

- 根拠: [`oriented_field_matcher.hpp`](../../include/oriented_field_localization/oriented_field_matcher.hpp)、
  [`oriented_field_matcher.cpp`](../../src/oriented_field_matcher.cpp) の`localize()` / `track()`
- 推奨: 計測値を呼び出し単位へ分離するかmutexで保護する。対応までは並行呼び出し不可と明記する。

### M6 — 評価ハーネスが条件の異なる古い生成物を再利用する

`eval/run_compare.sh`と`eval/run_reseed_margin.sh`は、POSES、地図、環境変数、source、compiler
flagが変わっても既存CSVがあれば再利用する。異なる条件の結果を新しい結果として集計し得る。

- 推奨: 常に再生成するか、全入力・source hash・設定manifestが一致する場合だけcacheを使う。

### M7 — 掲載する9地図・5400試行の表を公開物だけでは完全再現できない

Intel地図2枚は再配布条件未確認、廊下地図3枚は入手元・生成方法がなく、raw CSVと入力hashも
ない。公開物だけで再現できるのは合成地図である。

- 推奨: 再配布可能な公開dataへ置換する、生成器を同梱する、またはraw result・入力hash・
  実行設定を公開する。少なくとも完全再現できない範囲を明示する。

### M8 — simulation失敗を成功終了として扱う

`sim/run_sim.sh`と`sim/run_nav2.sh`は走行失敗を`|| true`で握りつぶし、retryを使い切っても
最終的に0で終了する。CIから失敗を判定できない。

- 推奨: cleanupを`trap`へ分離し、CSVの期間・行数・終了eventを検証して失敗時は非0で返す。

### M9 — 自動CIと実行環境の固定がない

GitHub Actions等のworkflowがなく、Docker base imageとapt packageもversion/digest固定されて
いない。同じcommitでも将来のbuild/test結果が変わり得る。

- 推奨: ROS 2 Humbleのbuild/test workflowを追加し、base digestと主要依存version、または
  少なくとも検証済み環境を記録する。

## 問題なしと確認した点

- `LICENSE`と`package.xml`はいずれもMIT。
- 現行追跡対象とGit履歴から、秘密鍵、API token、password、開発機の絶対pathを検出しなかった。
- maintainer/commit authorの氏名・mail addressは公開情報になるため、意図した連絡先かだけ確認が必要。
- 第三者地図、rosbag、評価CSV、log、build済みbinaryは追跡されていない。
- 追跡済みGIF/MP4は合計約6.2 MBで、通常のGit host上限に抵触する大きさではない。
